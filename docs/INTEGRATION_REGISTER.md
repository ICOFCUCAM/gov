# CivicOS — Integration Register

Everything in the platform that is built but still runs on a placeholder,
a demo value or an in-memory stand-in, and what it takes to connect it for
real. Keep this file current: **any change that adds a stub, a placeholder,
a demo value, a new external dependency or an integration point adds or
updates an entry here in the same change** (see `CLAUDE.md`).

Status: **Ready** = works for real once configured · **Partial** = real for
some cases · **Placeholder** = shaped correctly, not connected.

Last reviewed: 17 Oct 2026.

---

## 1. Platform and data

**One owner per register** (architecture review R19): each register has one authoritative store and one write API; every other copy is a mirror, a fallback used only when the owner is unreachable, or retired (kept reachable, never written). The decision is code, `app/src/lib/data/register-owners.ts` (served at `GET /api/platform/owners`); `register-owners.test.ts` fails when a new platform store or civic-api module has no owner, when a copy of a platform register is anything but a mirror (a civic-api copy in a mirror mode, fed or not), when a write civic-api forwards has no platform route with that method, when app code other than a mirror's writer writes a mirrored substrate table, and when app code reads one (its table, or an SQL function listed as reading it) instead of asking the platform; mirror fallback readers are listed per copy and there are none. Summary: the platform stores own the nation profile, institutions, directives, the platform audit chain, permits, payments, operations, federation, officials, the twin, facilities, boundaries, case loads, public sites and the Update Center; the substrate owns dispatches and escalations, the citizen runtime, identity, telemetry and its own audit trail. **Duplicates retired (finding D8):** the substrate's `civicos.directives` and `civicos.institutions` are mirrors of the platform, written only by `lib/db/mirror.ts` with the service role after the platform's change (best-effort; a refused record stays queued with its error, is retried on the next change and re-copied by the hourly `/api/cron/promote-directives`; queue and errors in `GET /api/platform/owners` as `substrateMirror`); migration `20261022000000_civicos_substrate_mirror.sql` adds `mirror_directive` / `mirror_institution` (service role only) and withdraws the old write RPCs from `anon` and `authenticated`, so no browser writes them (SQL check `supabase/tests/substrate_mirror_test.sql`). Directives a substrate held from before are taken over by the platform once, audited (`directive.adopt`). Every `services/civic-api` module is a **mirror of the platform** (1.38): reads answer from its own tables, which only its follower writes from the platform's signed events and the mirror feed (`GET /api/platform/mirror`); a write made to it is forwarded to the owning platform route with the caller's own credentials (`CIVIC_API_MODE=forward`, the default) or refused with 410 (`frozen`); writes with no platform route (citizen identity, provisioning another tenant) answer 410. No app code reads a mirror: the charter list, profile and detail, institutions catalogue, observatory and search read the platform's institution register through `GET /api/public/charters` (`lib/institution/charter-register.ts`; filters `activated`, `kind`, `charter`, `q`; first activation from the ministry registry's `activatedAt`, falling back to creation for records saved before it was kept, and the installation's launch for the standing institutions) and join the substrate's own rows (facilities, dispatches, escalations, officers, posture) by charter id; governance output (directive statistics and weekly trend) is computed from the platform's directives register (`lib/data/directive-stats.ts`, the SQL definitions, signed only) and served by `GET /api/public/accountability` (`?only=directives`, `?weeks`, `?directive_days`) with `directive_source` (reported, the directives register); search asks `GET /api/directives?q=`; the posture digest takes the activated charters from the platform. The substrate's `directive_stats`, `directive_trend` and the escalation cascade trigger still read the mirrors for the substrate's own use, kept and commented as such (migration `20261022100000_civicos_mirror_readers.sql`). Only the substrate's self-inspection (row counts on `/gov/substrate`, `/api/substrate/digest`, `/api/substrate/export`) lists the mirror tables, as tables (`SUBSTRATE_INSPECTION`). `/api/public/charters` and `/api/public/accountability` are open reads under `CIVICOS_AUTH=enforce` (the public charter profile and observatory read them).
